# Frontend build prompt — Cyber One

Build an accessible, responsive VPN control website for nontechnical families, using the shared contract in 03-API-CONTRACT.md. The backend owns every authorization decision and all persistent state. Never place server keys, passwords, backup codes or customer records in browser storage. Use a same-origin HttpOnly session cookie. Use real API responses; show actionable errors without pretending failed operations succeeded.

Visual direction: quiet blue-and-white layout, slate text, restrained blue accents, generous whitespace, large readable text, simple cards, small shield motif. No busy cybersecurity graphics or overwhelming data. Keyboard-visible focus, semantic labels, live regions, reduced-motion support, responsive mobile layout. Status must use text as well as color.

Implement these stages:
1. Home with Log in and Create account.
2. Registration: unique username, required recovery email, password entered twice, required sample-image step (PNG/JPG, up to 2 MB; basic server format validation, discard immediately). Clearly say that no actual ID verification occurs and never upload actual IDs. Production registration must fail closed until a provider is integrated; browser checks cannot prove identity or prevent duplicate people.
3. Show ten server-generated, globally collision-checked, case-sensitive 12-character codes as xxxxxx - xxxxxx. Show the full codes only on creation. Prominent reminder to write and store them safely, plus saved-codes acknowledgement. Disable Continue for ten seconds, show the remaining time, and keep it disabled until acknowledgement is checked. Enforce the initial delay on the server as well. Requested codes are reusable, not normal one-time recovery codes; explain the tradeoff.
4. Existing sign-in: username/password then one code. Every sign-in must then show privacy disclosure, terms, explicit checkboxes, and a typed name. Do not claim scrolling proves reading. Block account operations until server records consent for that session.
5. Connection page: prominent central toggle; Location selector, Auto, Off. Navbar: Connection, Account, Log out. Display temporary-profile state separately from real VPN connection. The delivered adapter is simulated: public IP remains unchanged, no network tunnel, restriction bypass or system-wide ad blocking. Never display “protected” based only on a database row.
6. Account: display name, notification preference (“Let me know if a problem occurs with temporary account data”), and up to eight linked family logins. Create family account opens a branded home-style registration page with name, unique username, password and confirmation; preserve the main session and link on the server. Show the new member’s own backup codes with a ten-second hold and return to the main account. Existing labels support Set up login. Mini users sign in independently with their own code and disclosure, share exactly one household temporary profile, and have limited account controls. Show each mini user’s VPN profile On/Off status on the owner account, refreshing every five seconds without replacing unsaved profile inputs. Distinguish simulated status from actual traffic protection.
7. Red Delete Account and Information button. Require exact phrase “Delete my account and information,” request a server deletion challenge, wait two seconds and then confirm. Temporary-profile deletion must be separate and clearly state its snapshot effects.
8. Logout invalidates the server session and returns home.
9. /admin for Laptop A, with separate administrator authentication. Show household counts, temporary-profile counts, ciphertext samples, snapshot times, manual backup/re-encryption, cutoff-based snapshot deletion with confirmation, and a visibly simulated incident action. Never show keys or sensitive plaintext. Operator-reported incidents pause profiles and appear on Laptop B within a five-second poll.
10. Controlled link lab: submit a URL to backend screening; show Blocked, Invalid or Unknown, never Safe for an unmatched link. Do not fetch links or ship live malware. Explain this is not browser-wide blocking.

Do not add analytics, third-party fonts, unnecessary permissions or actual ID collection. Keep critical incident notices visible regardless of optional toast preference. Put implementation limits where they affect a user's decision.

Email recovery: require an email for main and family signup, send verification, show verification state in Account, and allow existing full-session users to add an unverified address after entering their password. Login and code screens link to recovery. Offer username reminder, password reset, code replacement (current password required) and combined password/code recovery. Confirm verification explicitly. Use single-use expiring fragment links and remove tokens from the address bar. Never show debug recovery links. Replacement codes retain the ten-second hold and saved-code acknowledgement. Clearly explain missing delivery configuration and the trust placed in the recovery mailbox.
