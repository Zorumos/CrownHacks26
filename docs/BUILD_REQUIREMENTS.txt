**3. Shared state and fallback behavior**

**6. Multi-device connection behavior**

When a judge connects:

- Create or update their anonymous session.
- Count that session exactly once.
- Synchronize the count to the presenter and other participants.

Use idempotent requests and server-authoritative membership. Prevent duplicate clicks, retries, and reconnects from inflating the count.

Use heartbeats and expiration so abandoned sessions stop contributing. Do not rely solely on browser unload events.

Poll approximately once per second while visible, with sensible backoff and stale-state indicators.

Target approximately one-to-two-second synchronization under normal conditions. Measure actual results instead of claiming guaranteed instant delivery.

**7. Rolling encrypted-backup demonstration**

Use real **AES-256-GCM** through a supported cryptographic implementation. Do not present random hex strings as encryption.

Encrypt synthetic, non-sensitive metadata only. Never include real VPN private keys, passwords, physical IDs, browsing records, or sensitive account information.

Demonstrate an accelerated rotation every three seconds:

- Explain that this represents an illustrative hourly cycle.
- Generate a fresh encryption key and unique random nonce for each rotation.
- Encrypt a defined, canonical payload.
- Store ciphertext, nonce, authentication tag, rotation epoch, and necessary public metadata.
- Retain only the current demonstration key in application-managed state.

Include an identical-payload example showing that ciphertext changes despite unchanged plaintext. Distinguish key rotation, randomized encryption, and payload changes.

Do not claim changing ciphertext guarantees unlinkability.

Use atomic, request-driven rotation checks during polling. Do not rely on a permanent serverless `setInterval`. Explain that rotations do not execute independently when no requests occur.

Keep keys server-side in shared mode. Return only ciphertext and appropriate public metadata.

**8. RAM-only claims and panic protocol**

Present “RAM-Only Defensible VPN Node with Rolling Cipher Backup” as an architectural concept unless a real RAM-only deployment has been implemented and verified.

Redis, serverless memory, provider backups, logs, and persistence settings do not automatically establish RAM-only operation.

Display:

“This prototype demonstrates application-level key removal. It does not prove physical RAM erasure or deletion from provider backups.”

When a judge confirms panic:

- Atomically mark that room generation as panicked.
- Remove the current application-managed demonstration key.
- Set active simulated connections to zero.
- Reject subsequent connection, heartbeat, and rotation writes for that generation.
- Preserve the last ciphertext and freeze the inspector.
- Synchronize panic across all participating screens.

Show:

“DEMO PANIC ACTIVE: ACTIVE DEMO KEY REMOVED.”

Explain:

“The application no longer holds the current demo key. This does not prove that infrastructure copies or backups are unrecoverable.”

Do not claim verified physical memory erasure or permanent unrecoverability.

Handle panic racing with rotation, connection, and heartbeat requests. A stale operation must never restore a key or reactivate sessions.

Only the presenter can reset into a fresh generation with new keys and invalidated old-generation credentials.

Panic affects demonstration state only. It must not wipe disks, shut down a VPS, execute offensive actions, or delete real user records.
